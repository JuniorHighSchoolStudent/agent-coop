# 运行时与模型扩展约定

状态：设计合同，尚未实现。产品总体合同以 [design.md](design.md) 为准。

## 分离的配置维度

| 维度 | 职责 |
|---|---|
| Role | 目标、输入输出、允许职责与独立性要求 |
| ExecutionProfile | 绑定 runtime、provider/model、预算、权限及账号组 |
| RuntimeAdapter | 某类 agent 的启动、协议、事件、取消、恢复与能力探针 |
| ProjectAdapter | 项目事实、任务引用、工作目录及原证据位置 |
| GateAdapter | 项目原验证命令、验收条件与接收入口 |

原生模型网关由宿主 agent 管理时，profile 可以不单列 provider；需要显式 provider 的宿主则保留完整命名空间。适配器负责映射，不强行把所有模型 ID 变为一种格式。新增 profile 不新增角色类型，新增 runtime 不改工作流拓扑。

## 推荐执行者

用户指定的推荐为 CodeBuddy + DeepSeek V4-Pro，model ID 为 `deepseek-v4-pro`。2026-10-10 的本机 `codebuddy --help` 列出这个 ID，并支持 `--acp`、`--model`、`--settings`、结构化输出和会话恢复；[DeepSeek 官方文档](https://api-docs.deepseek.com/)也列出该模型 ID。

这只证明名称及宣告能力，未验证实际登录、配额、质量或使用成本。执行前 doctor 必须核对本机版本、所需能力及配置可用性；需真实模型调用的可用性检查应单独列明预算。不可用时返回明确阻断，不自动换用其他模型。不同任务的推荐可以由后续评测证据更新。

## 异构模型评审

推荐支持两组 CodeBuddy reviewer profile：GLM 负责项目适配主审，Kimi K3 负责执行/恢复合同主审，必要条目交叉复核。职责分工可由用户改变；模型名称本身不证明具备所需质量。

用户已确认逻辑名称 `glm3`、`kimi-k3` 对应本机提供的 `glm-5.3`、`kimi-k3-2`。这仅确认模型映射，不证明实际调用可用或评审质量。它们共享宿主也必须有独立会话身份；共享同一账号的并发与配额由一个账号组约束。Kimi Code CLI 监督者作为另一个 runtime/profile 配置，不与 CodeBuddy 的 Kimi profile 混称。

评审覆盖矩阵及版本门禁见 [design.md](design.md) §8.5。完整性以必需检查项均有有效证据衡量，不能按通过票数量或“没有发现问题”的自然语言结论判断。

## 根据配置清单与能力推荐

RuntimeAdapter 从宿主正式支持的模型目录、配置 schema 或 ACP configOptions 发现可选配置；缺少发现接口时允许用户显式登记，并标为手工来源。不扫描私有账户文件，不猜测 model ID，也不因名称相似合并不同 provider 的条目。

目录快照记录 runtime/version、provider/model ID、可选参数、来源、观测时间和有效期；区分宿主列出、账号可用及实际调用已验证。账号或网络不可访问时标为 unknown，目录过期时刷新或请求用户确认，不能显示仍然有效的绿色状态。

推荐过程先过滤角色必需能力、权限、预算、运行平台和输出合同，再比较适用的实测证据与用户偏好。编码、项目理解、审查、上下文容量、结构化交付、延迟与成本分别记录；能力宣告、官方说明、当前项目评测和用户经验保留不同来源等级，未知数值不填零，不生成没有证据的精确排名。缺少质量数据时只给出可行候选和待验证项；有预算后再开展有界评测。

建议输出候选 profile、适配理由、不满足/未知项、能力出处、目录快照、评测版本以及切换影响。推荐器作为可配置设计/intake 角色或确定性过滤流程，复用现有请求入口；用户选择后产生版本化绑定。多人评审的独立身份、异构模型要求及账号配额继续受 ReviewPolicy 和 Scheduler 管理。

目录刷新、模型下线或新模型出现只生成状态变化与替换建议；不能静默改变 active profile 或在途 attempt。自动选择只限用户预授权的候选集合和既定评测策略；用户这次确认三种推荐模型，不等于授权以后自动换模型。

## 适配器接口与准入

具体语言 API 由 P0 选定底座后确定，先固定语义：

- `probe`：获取版本和能力，区分 supported、unsupported、unknown。
- `start`：接收已经授权的 attempt、工作目录、profile、输入与预算，返回精确进程/会话身份。
- `events`：输出规范化进展、权限等待、工件、usage 和终态事件；不能将原始 token 输出当作有效进展。
- `cancel`：停止本 attempt 的工作并举证，不终止用户已有无关进程。
- `recover`：核对原会话与进程；原生恢复不可用时不得假装续接，改为受控的新 attempt 或人工接管。

manifest 声明 ID、版本、API 版本、配置 schema、能力和受支持平台。已有适配器支持的模型只需新增/切换 profile；新增 agent 通过本机明确安装的适配器注册。声明式配置不得注入任意 shell 命令，启动参数结构化传递。

接入前必须验证：正常结束与缺工件、结构化事件、取消及进程树清理、权限等待、恢复或明确不支持、错误/额度/认证状态、实际模型标识、未知成本、Windows 路径及 UTF-8。共享一套适配器合同测试，按能力选择场景，不为每家复制一份调度器。

## OpenCode 扩展

[OpenCode 官方 CLI 文档](https://opencode.ai/docs/cli/)提供程序化运行、会话及模型选择入口，也列出 ACP 命令。接入时必须根据安装版本探针选择 ACP 或结构化 CLI 传输，不能把网站示例等同本机验证。`provider/model` 应从用户实际配置与可用目录选择，不猜测供应商命名空间。

用户更换执行者时，先选择已注册适配器及模型，再核验原节点所需能力与权限。满足原合同的 profile 变更生成后继绑定；需要改变输入输出、权限、预算或流程时进入变更评审。已有 attempt 保持旧 profile；Web 显示“目标支持/已安装/能力已验证/实际调用已验证”的不同状态。

本机尚未验证 OpenCode，不安装软件、不自动导入其账号，也不宣称已经接通。其他 agent 依同一合同扩展。
