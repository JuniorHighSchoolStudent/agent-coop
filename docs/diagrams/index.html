图 1 / 总体架构

小内核 + 可插拔适配器

这张图回答：系统由哪些部分组成？谁有权写状态？项目里到底留下什么可审阅的东西？

01-architecture-overview.svg

  • 唯一写入者：三个入口（Web / 宿主插件 / 人工 CLI）共享同一后端，只有 coordinator 能发布工具状态；agent 提交具名 intent。
  • 内核固定：Scheduler（派发权威）、Monitor（只产事件，不决定重试/取消）、Store（SQLite 事务 + outbox）是三个职责模块，不是三个服务。
  • 边界插件化：RuntimeAdapter / ProjectAdapter / GateAdapter 承担宿主、项目事实与验证入口；内核不含任何业务规则。
  • 证据在项目里：coordination/ 是人工阅读入口；派生投影（STATUS、current.json）只由生成器产出，手改判为漂移。
图 2 / 设计思想

八条不变量

这张图回答：这套设计靠哪些不变量站得住？评审时按哪八条去反驳？

02-design-principles.svg

  • 八条按“谁写 → 谁权威 → 凭什么信 → 怎么扩展 → 怎么变好”排列，最后一条是明确不做的范围，防止首版膨胀。
  • 任何一条被打破，架构就不再成立：例如缺了“三类权威分开”，运行日志就会被误当成业务完成。
图 3 / 流程

需求与配置：从自然语言到合格节点

这张图回答：用户说一句话之后，系统凭什么保证它没被曲解、没被越权、真正进了队列？

03-request-to-dispatch.svg

  • 最小变更优先：先检索已有定义，再在「新任务 / 新参数 / 新角色 / 插入节点 / 新插件 / 新工作流」里选最小的一种。
  • 预览要说人话：不只给一句“已确认”，而是显示立即可执行的部分、等待的前置、在途任务保持不变的内容。
  • applied ≠ 已完成：它只表示定义或入队已生效，需求是否实现由项目原证据决定。
图 4 / 流程

一次执行怎么算完成

这张图回答：任务状态怎么流转？跨角色怎么交接？状态文件是怎么被“只写一次”地发布出去的？

04-execution-and-handshake.svg

  • 进程、会话、证据分开：exit 0 只证明正常退出，缺提交/产物/验证时不能进入 delivered。
  • 握手不是消息：offered → acknowledged → accepted/changes_requested/rejected；超时与失联不生成 accepted。
  • 单写 + outbox：事务提交 → 临时文件 → 原子发布不可变事件 → 发布带 revision 的投影；消费者比对 revision，不一致就显示 publication_pending。
图 5 / 闭环

知识积累与受控改进

这张图回答：踩过的坑怎么沉淀？什么时候允许它改变系统行为？

05-knowledge-loop.svg

  • 三层证据边界逐层收紧：Observation（已观察到的事实）→ Lesson（可复用经验）→ Improvement（具体补丁）。
  • 验证为真 ≠ 选择使用：反馈点赞不能晋级；没有证据的原因明确标 hypothesis。
  • 评测者与改进者分离：生成者不能改测试集或评分器；无实证改善不晋级，也不扩大权限。
