# 跨工作包流水线修订提案

状态：待独立交叉审核的后继设计，未生效、未实现；不改变任何在途调用的冻结输入或旧票效力。依据：用户要求发包人、执行者、审核者、监督者流水协作；当前状态唯一入口为[result.md](result.md)。本提案受审后，合同内容归并到[实施合同](implementation-contract.md)，派发次序归并到[派发计划](dispatch-sequence.md)，不建立第二调度器或状态台账。

## 1. 问题与选择

长期设计已经允许真实依赖驱动、固定交付的只读审核与其他实现并行，以及监督只阻断受影响工作。当前派发计划§3/§4/§6却要求批间串行、所有writer结束后才验证双审、整批齐备后才监督；运行时计划§4禁止跨批利用空槽。这些是额外流程屏障。

现有产品也未提供流水线：Runner持整轮锁并同步调用handler，Store.begin禁止并行running，失败使样例全局blocked。可复用Store事务、revision、事件/outbox、幂等发布与暂停底座；不能直接拆锁后并行调用旧样例Runner。

选择固定单包作为准入/接收单元，保留现有batch_id/packages/subject模型，每个单元packages只有一个包。B1–B4仅表示产品里程碑，不参与整批等齐屏障。确有原子组合必要的小组必须在准入前具名说明，不临时合并、删包或引入partial_accept。

另两种方案：保留大batch但提前逐包审核，仍会被大batch的版本变动与接收屏障牵制；增加更多作者但保留全局屏障，只增加等待库存。均不作为本轮默认方案。

## 2. 阶段和证据

每个已获设计准入的包独立流转：就绪→发包→实现→有效交付/验证→GLM与Kimi双审→完整监督材料→native监督→接收→解锁真实下游。两席可以并行；其他包在每个阶段继续推进。

- 每个单元的plan/dispatch/accept绑定相同包集合、准确base、policy、写集与依赖。计划票不能替代代码票；监督不能替代缺席、缺final或漏读。
- 一包有效final与准确验证就绪即可双审，无须等待其他作者。两席有效意见齐备即可监督；负面意见也纳入完整材料，不因不是双PASS而隐藏。
- 接收仍须该单元所有必要条件满足。负面意见、监督阻断或失败转交对应owner，由唯一发包人派修；不设固定总修复轮数，不盲重试。
- 修改包形成新准确候选，旧票对新候选失效；真实依赖该变更的消费者须重新核依赖。无关单元保持原准确依赖，不借新main/集成HEAD漂移失效，也不把旧票移植到新subject。
- 首版仅在真实上游准确接收后释放消费者；不把“接口已定”或“上游已交付”冒充已接收。源级准备可并行，执行准入和最终组合验证不得用替身结案。
- 集成者只在固定组合快照和接收CAS写入时持短锁，不持全局锁等待模型或测试。真实验证在不可变组合树锁外进行；接收前重核base/revision，漂移按影响重新验证。代码最终合并另有组合验证；模型退出、有效意见、接收和main合入分别报告。

注册配置不可覆盖。正常实现返修沿原单元追加attempt和准确候选；plan/base/写集/policy/依赖变化须建立重新准入及明确替代关系，保持同一request的用量和未闭合阻断，不通过换ID清账。上游新版本不会静默替换已有消费者的固定依赖；需要升级或因新finding受影响的消费者重新核验。接收receipt存在不证明消费者工作树已包含实现，基线须实际物化与核验。任一必需原票改变，重建bundle并重新监督。

## 3. 真实依赖与原包承接

保留原13包及唯一写集；本次用户要求补齐监控和业务职责后，新增M/T两个独立纯接口包，准确写集和接口以[基础合同](flow-foundation-contract.md)为唯一维护入口。N1/A/W/R1/S/M/T各自合同冻结且获得准确准入后可就绪；N2等N1；B等共享NativeTrace及N1/N2组合；F等B；C等A/B/F真实组合；R2等W/R1/N2；D等A/B/C/F和S，新增职责校验消费T；X等D/S/R2，监控驱动消费M；C2等独立接收的X，且必须通过真实产品入口派发。

| 原owner | 本次新增验收责任 |
|---|---|
| A/C | 固定单元的阶段/角色/依赖判定、准确证据装载，区分准入/交付/接收和失效范围 |
| S | 同一Store内阶段状态、就绪队列、原子claim、完成事件与后继就绪；统一资源和预算账 |
| D | 沿C/F为作者、两审核、监督与返修物化准确材料/角色绑定；不写第二队列 |
| X | 单一协调入口处理完成事件，立即补发已准入就绪动作，不等整批future结束；不持锁跨模型调用 |
| C2 | 运行、暂停、继续和状态沿同一X/S接线；真实派发dogfood前置保留 |

S在自身合同冻结且获准后可独立实现；D仍须等待其真实上游接收，接口只读准备不算作者启动。最终组合必须消费真实上游。单包超过可执行范围时按同owner顺序交付小片，不并行写同一store/runner文件。Codex负责集成和证据，dispatcher_next唯一派发，CodeBuddy deepseek-v4-pro实施，CodeBuddy glm-5.3与kimi-k3-2双审，native Kimi监督。

## 4. 容量、暂停与恢复

作者默认并行4路、用户可配置，不是整个团队只能4个agent或角色只能一个实例。角色是职责，实例按就绪工作创建；共享账号真实限制、用户显式并发配置、写入互斥分别声明，所有适用约束统一核算。此前“共享账号总容量4”仅是假设，不能当成本账号实测上限，也不能擅自给审核/监督再分固定人员编制。未知账号能力保持unknown，不等于无限并发或已满。暂停阻止新claim，以及已预留但未获启动许可的启动/Resume；暂停前已获许可且无法安全撤回的启动意图按design §7.8计入在途、继续对账，不因PID尚未可见当作未启动。容量降低阻止越新上限启动，不擅自杀已在途任务。

就绪队列沿design §7.1的优先级、同级等待顺序及老化规则实现公平性；资源不足的队首不能阻塞其他可运行节点。已交付包的审核/监督不能被持续新增作者饿死，审核积压时限制新作者补发；具体背压配置与选择规则由受审S/X合同定义，不在外侧另建循环。native独立账号当前只用1路；实际不可用或未知保持可见。

逻辑动作键区分request、固定单元、候选版本、stage和role，attempt是该动作的受管执行实例；不能更换attempt ID绕过同一逻辑动作的幂等与准入，合法返修引用原finding及后继准确版本。重复或乱序完成事件不重复扣预算、入队或启动；崩溃后的未知attempt先对账，不能承诺外部进程严格恰一次启动，也不能自动重跑。进程终态未知不释放资源。暂停期间可保存已在途结果；恢复时重核输入、依赖、权限、存活和资源后才派发未执行动作，旧就绪状态不自动构成当前许可。

## 5. 必须由执行者落地的回归

1. 快/慢两个独立作者以事件屏障控制：慢包仍running时，快包双审已启动；快包双审齐备后监督启动，不等慢包。
2. 一个包负面意见或返修时，无关包继续推进；旧票拒绝新候选，真实依赖消费者阻断；缺席、缺final或漏读不能接收。
3. 同一动作并发claim、重复/乱序完成、outbox发布失败及恢复：不重复资源计费或自动重启未知进程。
4. 暂停发生于claim边界、继续与容量下降时，保存在途结果且不越限新增；共享账号/文件资源统一核算。
5. 已接收X真实派发C2，并保存作者、双席、监督与接收证据。无模型测试通过不替代这次受管使用。

现有15项路径/runtime测试只验证原底座，不覆盖上述流水线验收。本提案本身不关闭GOV问题。

## 6. 生效路径

先独立交叉审查单元粒度、准确依赖/base、角色动作、资源核算及恢复语义；随后在既有合同owner落地准确schema差异，重新冻结后继候选。由唯一发包人提交CodeBuddy GLM/Kimi双审及native监督，意见绑定新版本，不能复用S6旧范围票直接放行。

必须同步修改：implementation中的batch_dependencies及bootstrap适用范围，dispatch-sequence的整批屏障，runtime-integration-plan的禁止跨批条款；将当前仅支持作者的development-action/author_bindings扩展为受审角色动作，审核与监督沿同一claim。singleton列表可复用现schema，但角色动作与容量属于新增合同，不能因改单元名称而声称已有实现。共享设计以准确ArtifactRef复用，逐单元仍满足各自policy必需席位；需评估准入材料和票据成本，不能把全部13包资料重复塞进每包。

本提案提出时在途的恢复评估只审其原40块输入，实际终态见result。行政修补与本提案分别对账；任何剩余阻断须明确影响范围及责任人，不能因“与看护有关”无限扩散成所有无关准备工作的全局停止，也不能未经裁定绕过实际共享运行风险。

## 7. 监控、工作包调整和补发闭环

沿design §7.1/§7.6/§8.1–8.2：R2提供真实运行观察，M确定性识别进展/证据/阻断事实，S在原事务内去重持久化。X按已激活触发策略派发诊断或拆包职责；D组织准确ChangeProposal，T检查职责与图结构，A/B/C核适用独立意见和证据。通过后S以expected_revision激活后继版本、记录RunAmendment，X立即补发就绪动作。任何一步失败都保留原有效定义和未决责任；不新建监控状态库或外侧派发循环。

“持续有输出但没有有效产物”“无执行者而有就绪包”“待审积压”“大包长期无检查点”是不同原因。观测只产生可追溯事实与请求提案，不自动认定必须拆包；语义责任者判断拆包、补审核实例、解除依赖或调查失败。按配置的事件/到期触发， unchanged tick不重复调用模型。

拆包提案必须保留父包验收义务、未闭finding、已用预算及替代关系；子包有明确功能边界、写集、接口、输入输出、依赖和恢复点。不能为了并行拆散内聚职责，不能因改包名清除阻断。旧writer未确认停止时不得重派同写集。权限、范围或必需判据变化继续走独立审核；通常就绪补发沿已批准模板，不每次重新设计审批。

新增闭环验收：监控到真实瓶颈→正确职责提出调整→双审/监督检查→准确新定义CAS激活→空闲执行者实际接到就绪子包；重复事件不重复派发，暂停仍采集，恢复先对账，无关包继续。M/T单测或样例模拟仅是分层证据，不代替真实闭环。

## 8. 协作职责与业务阶段职责

design §4.1/§4.2已经区分角色、实例、workflow槽位和领域合同；本次不新增另一套角色枚举。发包、实现、审核、监督说明协作责任；产品/范围、工程、体验、QA、发布/文档、复盘说明该工作必须完成的专业职责。一个无冲突角色可以承担多项职责，独立审核资格仍按真实actor/session及原policy判断，不能换名字自签。

具体业务规则仍由原项目WorkRef/ProjectAdapter指向的owner维护，例如ABM语义或交易策略判据；职责模板只引用合同与验收原件，不把领域规则搬入通用内核。T能检查声明及引用是否齐备，不能只凭一个业务角色名称或结构检查报告判定业务正确。

| 阶段职责 | 本次能力必须交付的内容 | 审核检查 |
|---|---|---|
| 产品/范围 | 瓶颈分类、可执行调整目标、保留父包义务；不追求为了满槽拆包 | GLM/Kimi均检查范围与退出判据 |
| 工程 | M/T纯接口、S单写、X唯一派发、安全切换及异常路径 | 两席均检查SSOT/SOLID/实际依赖 |
| 体验/DX | 为什么未派发、是谁处理、下一动作；暂停/继续及unknown的真实解释 | 后继C2入口需行为回执，纯模块不伪称UI已完成 |
| 实现 | CodeBuddy受派准确写集、有效final、测试实现 | Codex不代写产品代码或修补 |
| QA | 快慢包交错、阶段缺项拒绝、重复事件、暂停和旧writer未知反例 | 实际执行与独立判断分别举证 |
| 发布/文档 | 准确接口与未实现范围、迁移/回退说明 | 清单不给main/push/deploy额外权限 |
| 复盘/监督 | 这次零作者、漏读、无效输出及全批等待成为回归和受管实用证据 | 不用文档接收关闭产品缺陷 |
